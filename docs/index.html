Tunny documentation

Reference documentation for a programmable networking tool that routes selected traffic through reachable provider nodes.

Tunny core

Route selected traffic through providers.

Tunny keeps ingress, route matching, provider policy, health state, and egress transport in one core path. Serve is one way to expose that path, alongside the proxy and tunnel compatibility modes.

Ingress

Accept application or system traffic through HTTP, SOCKS5, or TUN without changing the core route decision.

Route matching

Match a destination hostname or resolved IP to a configured provider or an ordered provider policy.

Provider transport

Reach the selected provider through direct or Tailscale transport, then let it perform the final TCP egress.

Configuration

Production example: many routes, many providers.

The Serve node owns the route table and ordered provider policies. Each provider runs the same provider configuration on a separate reachable node or region.

Serve node: client.yaml

node:
  name: edge-client
  transport: tailscale

proxy:
  listen: "127.0.0.1:1080"
  http_listen: "127.0.0.1:8080"

tunnel:
  enabled: true

providers:
  japan: "provider-japan:7070"
  singapore: "provider-singapore:7070"
  us: "provider-us:7070"

routes:
  "api.example.com": japan
  "media.example.com": singapore
  "payments.example.com": us

route_policies:
  "stream.example.com":
    mode: failover
    providers: [japan, singapore, us]

health:
  enabled: true
  interval: 5s
  timeout: 2s
  failure_threshold: 2
  recovery_threshold: 3

Provider nodes: provider.yaml

node:
  name: provider-japan
  transport: tailscale

provider:
  listen: ":7070"

# Deploy the same file on:
# provider-singapore
# provider-us

Start one provider process on each provider node, then start Serve on the client:

# On provider-japan, provider-singapore, and provider-us
tunny provider -c provider.yaml

# On edge-client
tunny serve -c client.yaml

Provider readiness

Health checks that stay out of the data path.

Tunny sends a small PING through the configured node transport. A ready provider answers PONG. Thresholds keep temporary network noise from flapping routes.

  • Healthy eligible for new connections
  • Unhealthy skipped after repeated failures
  • Recovered restored after repeated successes
route_policies:
  example.com:
    mode: failover
    providers: [japan, singapore]

health:
  enabled: true
  interval: 5s
  timeout: 2s
  failure_threshold: 2
  recovery_threshold: 3

Use cases

Practical routing for real networks.

Tunny is useful when a destination needs a deliberate egress path, while the rest of the network should continue normally.

Multi-region egress

Send selected services through VPS providers in Japan, Singapore, the United States, or another reachable region.

Application routing

Give browsers, scripts, and services HTTP or SOCKS5 access without changing the host's default network path.

System traffic

Use transparent TUN ingress for selected system traffic where the operating system supports the required device access.

Provider resilience

Order provider candidates, check readiness with PING/PONG, and fail over new connections when a provider becomes unhealthy.
